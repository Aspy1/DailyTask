# 汇报机制调研：主流 agent 怎么把"做了什么"讲给用户

调研日期：2026-10-19。目的：为**乙方案**（代码写事实、模型只补一句说明）找可抄的实现。

## 结论先说

四家做法**结构一致**：**消息是结构化条目，工具/改动的展示行由 harness 生成，模型的话只是其中一条**。
没有一家把"模型那段自然语言"当作"做了什么"的唯一来源 —— 这正是我们要抄的骨架 ✓。

## 抄什么（有出处）

### 1. 消息 = **结构化 parts/items**，不是一坨文本

- **opencode**：`MessagePart = TextPart | ReasoningPart | ToolInvocationPart | SourceUrlPart | FilePart | StepStartPart`
  （`packages/opencode/src/session/message.ts`）—— 助手文本只是 `text` 一种 ✓。
- **Codex CLI**：`codex exec --json` 的 item 类型：
  `agent_message` / `reasoning` / **`command_execution`** / **`file_change`** / `mcp_tool_call` /
  `web_search` / `todo_list`（`openai/codex/docs/exec.md`）。

→ 我们抄：**把"发生了什么"做成结构化条目**，而不是继续在模型那句话后面拼字符串 ✗。

### 2. **展示行由 harness 生成**（带证据字段）

- **opencode**：每个工具调用在 `MessageMetadata.tool` 里存 harness 生成的
  `{ title, snapshot, time: { start, end } }`；UI 侧 `ToolInfo = { icon, title, subtitle }`
  也是按工具名 + 参数拼出来的（`packages/ui/src/components/message-part.tsx`）。
- **Codex CLI**：`command_execution` 条目直接带
  `{"aggregated_output": …, "exit_code": 0, "status": "completed"}` ✓ —— **退出码与状态是结构字段**，
  不是让模型转述的 ✗。

→ 我们抄：事实行**由代码生成**，并且**带上机器可核对的值**（我们的对应物是 before → after）。

### 3. 模型的话只是**其中一条**，不是报告本身

- **Codex**：默认"把活动流写 stderr，**只把 agent 的最终消息写 stdout**" —— 两个通道分开 ✓；
  TUI 里 `agent_message` 与 `command_execution` / `file_change` **并列显示** ✓。
- **opencode**：`AssistantMessageDisplay` 把 parts 逐个渲染（`text` 与 `tool` 各自成块）✓。

→ 我们抄：**事实块与模型的话在视觉上分开**，事实在前、模型的话标注为"说明" ✓。

### 4. 要一句描述时，**把证据交给模型**让它描述

- **aider**：`get_commit_message(diffs, context)` —— **把 diff 与上下文发给（弱）模型**，
  让它产出 commit message（`aider/repo.py`）；用户侧用 `/diff` 看真实改动 ✓。

→ 我们抄：如果还要模型那句话，就**把回执/事实块作为输入**给它，让它**只描述这些** ✓
（它编不出没给它的事实 ✓）。

## 要自己补的（本项目特有）

| 差异 | 我们的做法 |
|---|---|
| 证据不是 **diff**，是**领域状态**（余量 / 位置 / 完成标记） | 已经有 `ai_verify.observe/check` ✓ —— 把 `before → after` 提出来就是事实行 ✓ |
| 工具结果**没有结构化回执**（CLI 契约是纯文本 ✗） | 短期：命令文本 + **回读数据**凑出回执 ✓；长期：让 handler 返回结构化结果（审查 §3.2 的 ActionReceipt）✓ |
| 没有 `todo_list` 等价物 ✗ | 账本（`ai_ledger.Ledger`）承担 ✓（§3.1 TaskRun ✓） |
| 我们的"命令"是**中文语义动作**（记物品 / 扣减 / 移动），不是文件编辑 | 事实行的措辞要**按操作类型**写（"移动 X：A → B" ✓），不能照抄 diff 风格 ✗ |

## 乙方案：给用户看什么（落地设计）

```
【已执行】                            ← 全部由代码生成（账本 + 回执），模型不参与
  记入 牙膏 1 瓶 @卫生间柜子            ✓
  移动 羽绒服：衣柜左1 → 家             ✓
  扣减 布洛芬：24 片 → 23 片            ✓
  ⚠ 设置提醒：保存被拒，没有生效         ✗
  未核对 2 条（没有验收器：add_task…）    ← 明说"没核对"，不写成"已完成" ✗

【说明】                              ← 模型的话（可选），只能解释上面这些
  过季收好，来年要寄回学校时说一声。
```

**四条规则**：

1. **事实行由代码写** —— 来源是账本里每条写命令的 `state` + 验收的 `before → after` ✓；
2. **模型那句只能解释、不能新增完成项** ✓ —— 它的输入就是事实块（aider 的做法 ✓）；
3. **两者视觉分开** ✓ —— 避免"模型的话看起来像报告" ✗（这正是这次那个 bug 的形态 ✗）；
4. **没验收器的操作明说"未核对"** ✗ —— 不许把"命令返回 OK"写成"已完成" ✗。

**边界情况**：纯查询/闲聊时**没有写命令** → 事实块为空 → 只显示模型的话 ✓（与现在一样 ✓）。

## 落地三步（按依赖顺序）

1. **回执结构化**：`ai_verify` 的 verdict 带上 `before → after`（现在只有一句话 ✓）→ 生成事实行；
2. **改渲染**：`AIWorker._report()` 里事实块在前、模型的话在后并标注 ✓（这一步就实现了 乙 ✓）；
3. **扩大验收器覆盖面**（现在只有 `consume` / 移动 / `complete_plan` 三条）——
   否则事实块会大面积"未核对" ✗，价值打折 ✓。
