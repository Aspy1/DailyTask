# 桌面体验与性能改造操作手册

先复现并定位卡顿，再用相同场景比较方案，最后按功能分批发布。现有 PySide6 作为对照。周视图用于试验视觉方案，作业用于试验 SQLite，两条试验单独测量和提交，便于判断收益来自哪里。

## 1. 准备环境与复现场景

1. 以通过门禁的提交为基线，记录提交号、Windows 版本、Python、Qt、运行时、CPU、内存、电源模式、DPI 和窗口尺寸。Web 方案额外记录渲染引擎版本。用工作区内的隔离目录和合成数据，数据写入测试采用 `sandbox`。禁用真实邮件、微信投递和 Git 数据同步，使用本地替身验证调用。
2. 固定三档数据量，例如 1 千、1 万、5 万条，记录实际字节数、学期分布、任务状态和附件数量。加入空学期、长备注、重复课程名、历史数据和大批量已完成任务。单文件 5 万条用于压力测试，业务规模另行记录。
3. 定义操作起止点和成功条件。把冷进程、热进程、首次切页和重复切页分开。同一轮固定网络状态，另测一次离线和网络慢的表现。冷启动记录是否重启系统或清理了相关缓存。

| 场景 | 从哪里开始 | 到哪里结束 | 并行记录 |
|---|---|---|---|
| 启动 | 父进程发起应用 | 首页可见且能接收第一个操作 | 首帧、首屏请求、后台初始化、进程树内存 |
| 切页和换周 | 点击、快捷键或滚动输入 | 正确数据可见，页面接受下一次操作 | 首次与重复、卡住最长时间、绘制次数 |
| 作业完成／改备注 | 用户提交 | 可见反馈和持久化确认分别记时 | 排队、锁等待、提交、刷新、错误反馈 |
| 学期切换 | 确认选择 | 日程与作业显示同一目标学期 | 旧异步结果是否覆盖新页面 |
| 外部数据更新 | CLI 成功提交 | 桌面显示正确版本 | 轮询等待与实际重载分别计时 |
| 常驻与退出 | 启动后等待、重复切页，再退出 | 记录稳定内存和退出结果 | 子进程、线程、句柄、未完成写入 |

**常见注意事项**：按钮反馈、数据写入成功和内容绘制完成是三个不同事件。界面可以先显示处理中，成功提示要等提交确认。已有合成单文件保存基线为 1 千条 12.9 ms、1 万条 86.4 ms、5 万条 420.4 ms，分别是 7 次的中位数。它可用于复核保存路径，不能推算真实启动或交互延迟。

## 2. 逐层定位卡顿

### 2.1 先记录端到端时间

1. 用单调时钟 `perf_counter_ns()` 在操作入口计时，之后给排队、取数据、等待锁、解析、写盘、信号分发、布局和绘制打点。每次操作使用同一关联 ID，遇到线程切换也要保留 ID。
2. Qt 主线程加轻量事件循环采样，按预定触发时刻与实际回调时刻的差值估计阻塞。首帧和可交互状态用有明确条件的标记，另用真实窗口操作复核。Web 端用浏览器 Performance 面板观察长任务、布局和帧，并把浏览器测量和宿主计时按请求 ID 对齐。
3. 先做 5 次试跑检查计时是否完整。可重复的操作建议每个条件至少 50 次，重点方案尽量达到 100 次。启动等高成本场景样本少时，明确报告样本量并逐笔检查尾部。记录中位数、P95、最大值、失败次数和内存峰值。交替跑基线与候选，保留原始样本。诊断 trace 与正式计时分开跑。

### 2.2 根据证据继续排查

| 看到的现象 | 下一步 | 在本项目优先检查 |
|---|---|---|
| UI 停住且 Python CPU 高 | 用 cProfile 找累计耗时和调用次数 | 初始化多个面板、整份 JSON 序列化、重复信号刷新 |
| UI 停住但 Python CPU 低 | 查线程等待、磁盘和外部进程，用 WPR/WPA 对齐时间线 | 文件锁、提交/备份、同步网络、退出等待 |
| 后台操作结束仍未显示 | 区分队列耗时、事件循环延迟和绘制耗时 | 跨线程 signal、分页重建、QSS 触发全局重绘 |
| 仅首次切页慢 | 记录页面构造、字体、资源解码、Web Runtime 启动各段 | `MainWorkspace` 初始化、延迟加载候选 |
| 每隔几秒出现停顿 | 同时观察空闲事件循环、轮询和重载次数 | `DataManager` 约 3 秒轮询、文件异常后重试 |
| 内存反复上涨 | 对比多轮同一操作前后的稳定值，追踪对象和进程树 | Qt 控件引用、线程回收、Web 渲染子进程、缓存边界 |

**常见注意事项**：采集仅存操作类型、耗时、大小、版本和错误类别。任务内容、凭据和绝对用户路径不进入共享 trace。Qt 或 Chromium 的原生内存需使用系统指标，`tracemalloc` 只用于 Python 分配。记录内存口径，例如进程树私有提交量，避免把共享页的工作集重复相加。 [Python 性能剖析](https://docs.python.org/3.14/library/profile.html) · [Windows 性能工具包](https://learn.microsoft.com/en-us/windows-hardware/test/wpt/) · [WebView2 性能指南](https://learn.microsoft.com/microsoft-edge/webview2/concepts/performance)

定位完成的证据包括复现步骤、基线提交、数据档、一个有代表性的慢样本、耗时最大的环节和可以用实验推翻的原因。先用一次小改动或替身隔离该环节，再决定进入哪条试验。

## 3. 试验和选型

### 3.1 方案 A 在 Qt 中消除阻塞

1. 首屏只构造必要面板，让其余面板首次进入时初始化。分别测首屏和首次切页，观察延迟是否集中到了某个常用页面。
2. 把轮询探测与解析、锁等待或保存移出主线程。后台只交付结果，控件更新仍在主线程。切页和换学期时给请求附上版本或目标学期，主线程丢弃过期结果。
3. 合并同一操作造成的多次刷新，按数据域和变化行更新。用计数器对比信号次数、重建行数和结果正确性。
4. 逐项试验，保留每项改动前后的结果。检查失败后控件恢复、退出等待和重复点击。异步提交须保留原有冲突、回执及异常处理。

### 3.2 方案 B 周视图 Web 原型

WebView2 宿主对照、同口径夹具和准入条件见 [WebView2 周视图迁移准备](WEBVIEW2_MIGRATION.md)。

1. 固定日程查询和同一份主题令牌，做只读周视图。比较当前 Qt、Qt 内嵌 Web 页和 WebView2 候选。WebView2 先验证宿主集成、运行时缺失时的行为、离线启动及应用退出。原型先采用本地资源和单个 Web 实例。
2. 用相同中文内容、窄窗口、深浅主题和 DPI 做截图对照。手动测试键盘焦点、滚轮、快捷键、减少动效设置、空态、错误态和连切周。核对长课程名、同节次冲突、已过期学期。
3. 测宿主与页面两侧时间。记录首帧、数据呈现、换周 P95、空闲及峰值进程树内存。试验“一次传当前周的数据”与必要的增量刷新，避免每个格子跨桥请求。
4. 保持受控消息契约，包括来源校验、固定操作集合、参数校验、请求 ID 和有界返回。外部链接用系统浏览器打开，导航到外部页面时不提供本地业务桥。现有 Qt UI 规范入口继续使用，跨栈共用令牌和文案规则。 [WebView2 安全实践](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/security)

### 3.3 方案 C 作业 SQLite 原型

1. 让现有业务读写入口调用存储实现，在隔离副本中以学期和作业 ID 保留身份关联。用版本化 schema、约束和必要索引，先验证作业状态、截止排序、附件元数据和历史条目。
2. 使用相同数据对比 JSON 与 SQLite 的按学期列表、未完成筛选、分页、单条完成、批量导入和启动读取。对常用 SQL 检查查询计划。分页排序包含唯一的稳定排序键，避免跨页重复或漏项。
3. 对 SQLite 分别验证短事务、连接归属、并发读写、超时和失败回滚。每个线程持有自己的连接，写事务尽量短。若采用 WAL，验证同机进程、运行时版本、长读事务引发的 WAL 增长、检查点尾延迟和锁竞争。桌面、CLI、Hermes 都使用同一业务校验；对可能已提交的失败或超时保留请求 ID 并核对结果。
4. 保留当前 JSON 作为导入来源，数据库备份走 SQLite 在线备份 API，验证快照可恢复。附件用独立文件并验证引用。检查私有 Git 工作流、每日摘要、Hermes 提醒和备份恢复所有消费者，逐一决定走业务查询还是受控的只读 JSON 导出。运行中的数据库文件和 WAL 不充当跨机器同步协议。 [SQLite WAL](https://sqlite.org/wal.html) · [SQLite 在线备份](https://sqlite.org/backup.html) · [SQLite 查询计划](https://sqlite.org/eqp.html)

### 3.4 决定是否实装

每个方案填一份决策记录，写清影响的场景、对照提交、样本量、中位数与 P95、失败数、进程树内存、代码和交付成本、保留或放弃理由。试验前先为主要指标定预算，例如要求重负载下作业操作 P95 至少改善 20%，同时为首屏和稳定内存约定可接受的额外开销。这些是项目试验阈值示例，具体数值以基线和机器能力确定。数据正确性、退出、离线启动和恢复成功单独验收。

## 4. 实装与上线

1. **先写回归测试再动代码。** 覆盖当前失败、慢路径和失败恢复，模拟现有入口的完整信号与数据链。按 `AGENTS.md` 读架构、错误索引、代码规范和受影响源码，动 UI 前读 `design/INDEX.md`。
2. **分提交上线。** 将测量、Qt 优化、Web 页面和数据库迁移拆成可审查提交。Web 先保留 Qt 入口作为回退；有数据编辑前先验消息、错误提示和键盘行为。数据库每次只为明确的业务域切换权威存储。
3. **演练数据库切换。** 在沙箱执行“预检 → 备份 → 暂停该域写入 → 导入 → 核对 → 切换消费者 → 恢复写入”。核对学期、记录数、稳定 ID、关键字段、附件和提醒查询结果。测试重复导入、导入中止和旧 schema。切换前回退可恢复旧入口；新库接受写入后，回退须先冻结写入，备份当前库并通过验证过的导出或变更回放保住新增数据。旧快照只能恢复到其创建时点。
4. **按项目门禁验收。** 在 Git Bash 用项目解释器跑 `./.venv/Scripts/python.exe scripts/ci_local.py --keep-going`，覆盖编译、Ruff、UI 令牌、严格质量门禁、依赖一致性、合成验收和 pytest。之后在实际可见窗口复跑目标场景，检查离屏测试无法覆盖的 DPI、焦点、真实绘制和 WebView 子进程退出。按项目约定确认 Windows 双版本和锁文件复现，再把经过验证的提交合入主分支。
5. **发布后复核。** 测首启、后台提醒、桌面与 CLI 并行、退出和重新启动。监测尾部延迟、写入错误、内存与备份恢复。出现数据对不上、请求重复生效或常用操作显著回退时，暂停扩展，按 UI 和数据各自的回退步骤处理。

## 5. 每一批需要保留的记录

- **定位记录**：用户操作、环境、数据档、慢样本、时间线、根因证据。
- **试验记录**：改动范围、对照数据、失败样本、视觉截图、收益与代价、选型结论。
- **发布记录**：回归测试、门禁链接、迁移与回滚演练、已切换消费者、未完成事项。
- **复用位置**：阶段记录进 `dev-logs/`，新增失效模式进 `ERRORS.md`，数据流和并发变化进 `ARCHITECTURE.md`。测量稳定后再推进 `PLAN.md` 的 I-15，优先在可控机器做性能趋势，公共 CI 做正确性和明显回归检查。

|---|---|---|---|---|---|
| 示例：1 万条作业，连续完成单条 | 提交 P95、UI 阻塞 | 待测 | 待测 | 待测 | 关联原始样本与慢操作时间线 |
