# 2026-10-19 AI 架构第 ③ 步：动作账本 + 错误分类恢复

## 起因

`PLAN.md` P22「AI 侧后续」第 ③ 条：专项审查 §3.1（TaskRun）/ §3.4（RepairPolicy）/ §2.3（恢复表）。

两件事：

1. **账本**：完成率要按**目标**算，不能用"成功命令数 ÷ 总命令数"充数 ✗；
2. **分类恢复**：ERROR 要**分类**，连"该做什么 / 不能做什么"一起回喂模型 ——
   原来只把原文丢回去，模型只能猜，而 α 测试里真实出现过三种猜法 ✗：
   **原样重发同一条**、**猜一个 id**、**为了让命令过自己加 `--yes`**。

## 做了什么

新模块 **`src/services/ai_ledger.py`**：

| 部分 | 内容 |
|---|---|
| `Ledger` / `Goal` | 逐条**写命令**记状态（查询不算目标）；`counts()` 按状态分组；`summary()` 一句话账本；`is_clean()` |
| `STATE_LABEL` | 状态 → 中文（`验收通过` / `本来已满足` / `没达到预期` / `执行失败` / `被阻塞` / `未验收`） |
| `classify_error(result)` | 把 ERROR 归类 → `(类别, 该做什么, 不能做什么)`；**归不到就明说"未分类"**，不硬套 ✓ |
| `recovery_note(results)` | 给失败的那几条配上恢复建议（同类去重；没有失败就返回空串） |

**状态从哪来**：账本的状态**来自验收**（`ai_verify` 回读数据），不是"handler 返回 OK" ✓ ——
这是与"成功命令数"最本质的区别 ✓。

**分类的关键词取自 `scripts/` 里真实出现的 ERROR 文案**（不是凭想象写）：

| 类别 | 该做什么 | 不能做什么 |
|---|---|---|
| 参数不合法 | 按字段级错误改参数后重试 | 原样重复同一条命令 |
| 对象已存在 | 用 `update_item` 改那一条（回执里有 id） | 为了"记上"再建一条同样的 |
| 对象不存在 | 先查询候选（`lookup_item` / `list_*`）或向用户澄清 | 猜一个 id，或擅自新建替代对象 |
| 保存冲突 | 重读最新状态、保留原意重算 | 关掉冲突检测硬覆盖 |
| **需要用户授权** | 把这条**转达给用户**，等他们自己确认 | **自己加 `--yes` 替用户拍板** |
| 数据异常 | 保留已完成部分，如实说明卡在哪 | 绕过合法入口去改文件 |

**接进 worker**：
- `_run_commands` 多收一个 `ledger` ✓，逐条记**写命令**的状态 ✓；
- 工具结果后面附 `[恢复建议]` ✓（模型这才有"下一步怎么办"，而不是只有原文 ✗）；
- 收尾抽出 `_report()` ✓：剥代码块 → **不干净时**才附账本 → 走统一 `_finish()` ✓；
- 账本**每次都进日志**（`logger.info`）✓，给用户看的只在"不干净"时加 ✓（别添噪）。

## 诚实边界

- 账本的"目标"粒度 = **一条写命令** —— 自由文本请求的**目标分解**需要模型参与，
  属后续工作（审查 §3.1 也承认"任务分解本身也可能遗漏要求"）；
- `RepairPolicy` 的"**有界**"目前复用既有的重复阶梯（`repeat_nudge`）+ 轮次/时限预算 ✗，
  还没有"每个失败目标分配 N 次修复机会"的**逐目标**计数 ✗；
- `classify_error` 是**关键词分类** ✗ —— 精确的类别要执行层返回结构化错误码（同第 ② 步的边界）。
