# 2026-10-19 R9：手机号按可复用 ID 关联（删后重建串号）

## 起因

`PLAN.md` P22 批次三第一条（`REVIEW.md` R9）。

手机号是 PII，单独放 `data/private/memberships.json`（不进仓库、不进提示词），
**按物品 id 关联** ✓。但物品 id 的老生成方式是**挑最小的空缺号**：

```python
n = 1
while n in existing:
    n += 1
iid = f"i_{n:03d}"        # ✗ 删掉 i_001 再新建 → 又是 i_001
```

于是：删掉带手机号的 `i_001` → 新建一条会员 → 新物品拿到 `i_001` →
**旧手机号串到新物品上** ✗（用户会看到别人的号码挂在自己新记的会员上）。

## 改法：id **只增、绝不复用**（根因）

```python
def next_item_id(data: dict, items: list) -> str:
    seq = data.get("item_seq")
    if not isinstance(seq, int) or seq < 0:
        seq = max((item_number(it) for it in items), default=0)   # 老文件按最大号初始化
    seq += 1
    data["item_seq"] = seq
    return f"i_{seq:03d}"
```

- 序号**存在数据文件里**（`item_seq`）→ 存盘、重启、跨天都不会回到已删的号；
- 老文件没有这个键 → 按现有最大号往后接（向后兼容，不与已有 id 冲突）；
- 放**模块级**而不是类方法：`InventoryModel` 正好卡在类的尺寸上限（400 行），
  加进类里会直接把门禁顶红（这次实测踩到了，见下）。

**配套的卫生**：新增 `MembershipContactsModel.forget(iid)`，UI 删除与 CLI `delete_item`
各调一次 —— 但**关键不是它** ✗：id 一旦复用，"删的时候顺手清一下"挡不住
（备份/同步恢复、CLI 删除、异常中断都可能漏），所以根因必须靠 id 不复用来堵。

## 验证

新增 `tests/test_inventory_item_identity.py`（**6 条**）：

- 删 `i_001` 再建 → 新 id **不是** `i_001`；
- 序号存盘：重新读盘后继续往后接（删 `i_002` 之后新建拿到 `i_003`）；
- 老数据文件没有 `item_seq` → 按最大号接（`i_007` → `i_008`）；
- `next_item_id` 纯函数行为；
- **端到端串号场景**：删掉带手机号的会员 → 新建会员 → 号码不跟着走，且旧物品的记录也清了；
- CLI `delete_item` 会清私有文件（那是 AI / TG 那条写入路径）。

**679 passed**；`ruff` / `ui_tokens --strict --check-px` / `check_quality --strict`
全绿（**退出码全 0**）。

> 说明：这次的"旧代码会红"没做成行为断言 —— 旧代码里根本没有 `next_item_id`，
> 回滚后测试在**收集阶段**就 ImportError 了。也就是说测试确实钉在新实现上，
> 但"旧实现会怎样错"是靠代码阅读与审查复现确认的（老逻辑一眼可见）。

## 踩到的门禁（值得记）

把 `_next_item_id` / `_item_number` 写成**类方法**时，`InventoryModel` 从 ≤400 涨到 **415**
→ SIZE 直接红 ✗（它是"新增超限项"，不在基线里，没有豁免）。
挪到模块级后回到 400 ✓。这条与 R5/R6 是同一类：**这个仓库的类/文件尺寸上限会真实地
塑造代码放哪儿**，不是装饰。
