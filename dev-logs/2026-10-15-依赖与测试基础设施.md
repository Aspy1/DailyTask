（`openai<4`、`anthropic<2`）并确认 API 面存在，但未做真实调用验证。

## 测试固化的已知缺陷（xfail，非 strict → 修复后自动 XPASS）

1. `scripts/actions.py` `cmd_add_item`：`qty = args.quantity or 1`
   把 `--quantity 0`（已用完）当成缺省值 → 记为 1 件"充足"。
2. `SYSTEM_PROMPT_BASE` 宣传 `query_weather` / `query_balance` / `weather_stats`，
   但 `actions.py` 无对应 handler → AI 调用只会得到 `ERROR unknown action`。
3. `delete_item` 有 handler，但 `main()` 未注册 subparser →
   `python scripts/actions.py delete_item ...` 会 argparse 报错（内存调用正常）。

> 上述 2、3 属"第 2 步：AI 命令表对齐"的修复范围；1 建议一并修。

## 环境备注

- 本机到 pypi.org 的 wheel 下载极慢（约 88 kB/s，PySide6 全套 125MB 需 25–40 分钟），
  改用清华镜像 `-i https://pypi.tuna.tsinghua.edu.cn/simple` 重装（单次参数，不改全局配置）。
- 切换 venv 后，开机自启注册表仍指向 anaconda 解释器；应用每次启动会按 `sys.executable`
  重写该注册表项，因此**用 venv 解释器启动一次**即可自动纠正。
- 排查中的一个坑：`openai`/`anthropic` 构造客户端会经
  `httpx2 → httpcore2._ssl → import truststore → platform.system() → subprocess(["cmd","/c","ver"])`。
  本机 `HKCU\...\Command Processor\AutoRun` 挂着 conda 钩子，CPU 被别的进程占满时
  这条 `cmd` 子进程会被拖到分钟级，表现为"AI 客户端构造卡死"。经确认是**瞬时 CPU 饥饿**
  （另一项目的 `p5_matrix.py --workers 16`），负载正常时 `platform.system()` 仅 0.7s、client 构造 1.7s。
  → 与代码无关，但说明：本机跑应用时不要同时跑满 CPU 的重任务，否则 AI 功能启动会假死。

## 教训

- "没有测试"时，口口声声的功能其实是"没验证的假设"——刚建好冒烟测试就抓到
  `--quantity 0` 这个静默错误。
- 依赖声明要覆盖"实际 import 的库"，而不是"记得的库"。
- 默认 PyPI 在本机不可用（吞吐极低）时，应尽早换镜像，避免误判为"卡死"。
