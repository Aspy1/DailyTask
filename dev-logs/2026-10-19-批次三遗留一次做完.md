# 2026-10-19 批次三遗留：一次做完四条

`PLAN.md` P22 批次三里"另外确认的遗留/边界问题"。四条一次处理完，各自带回归测试。

## 1. 提示跨天不清理

`HintBar._dismissed` 是一个**裸 key 集合** ✗，配套的 `clear_dismissed()` **全仓没人调** ✗ ——
常驻应用跨天后，昨天关掉的雨天/出门提示今天还被过滤着。

**改法**：把"点掉"记在**当天**名下（`_dismissed_on`），而 `show_hints()` 是唯一出口 →
跨天自己失效。**根治方式不是"记得调清理函数"，而是让它不需要被调**。
顺手删掉 `clear_dismissed()`（已成死代码）。

## 2. 预算统计没有日期上限

`_spent_since(records, since)` 只筛 `date >= since` ✗ → **未来/下月**的记录会算进"本月已花"
和"近 90 天日均"。复现：只记一条 `2030-01-01` 的 1000 元 → `spent=1000`、`projected=1144` ✗。

**改法**：
- `_spent_between(records, since, until)` —— **闭区间** ✓（本月已花 / 历史都封到 today）；
- `history_days()` —— 日均的分母改成**实际有记账的天数**（从最早一条算起，封顶 90）✗，
  不再固定除 90（那等于把"还没记账的天"当成花了 0 → 日均偏低 ✗）；
  `forecast()` 结果里多一个 `history_days`，让界面能看出"样本不足"；
- `renewals_soon()` —— **已经过期的**不再算"即将扣费"（`0 <= days <= 30`）；
  那个日期已经过去了，它属于"要续费"（状态"需购"那条路），列在这里会让人以为马上要扣钱 ✗。

## 3. 墙钟预算是软检查

`max_seconds` 只在**每轮请求之前**检查 ✗，而单次 SDK 调用本身可能超过它
（provider 侧超时 120s，且可能重试）→ 不能承诺"90 秒收尾"。

**改法**：审查给了两条路（"改文案"或"真约束"）。选**改文案 + 写清口径** ✓：
在 `_max_seconds()` 的 docstring 里明确"**软**上限：到点后不再发起新请求，
已执行的命令结果照常保留并如实汇报；**不做"超时就回滚"的承诺**（副作用已经落在 JSON 里）"。
真约束要改 `AIProvider` 协议（3 个 provider）传剩余预算 —— 收益不抵改动面，记在这里备查。

## 4. 门禁基线可被"此处减、彼处增"绕过

三处都是**总数**口径 ✗：`ui_tokens_baseline.json` 是 `{"px": 166, "size_lit": 49}`，
`quality_baseline.json` 的 `ui_chinese_literals` 是 `102` —— 只要总数不涨，
"这里少一处、那里多一处"完全看不出来 ✗。

**改法**：
- `check_ui_tokens.py`：`_scan_files` 多返回一份 **按类型×文件** 的计数 ✓；
  基线改成 `{"px": {文件: 处数}, "size_lit": {…}}` ✓；新增 `_over_baseline()` 按**文件**比 ✓；
  **基线缺失 / 读不出来 → 直接失败** ✗（以前"无基线可比"会悄悄放行 ✗）；
- `check_quality.py`：`count_ui_chinese_literals_by_file()` ✓ + `report_i18n` 按文件比 ✓；
  新增 `BASELINE  存量基线文件存在` 这条硬检查（缺失即失败）✓。
- 两份基线已用 `--write-baseline` / `--write-px-baseline` 重写（**债只减不增**：
  px 166 → **161**、size_lit 49 → **47** —— R2/R6 顺手修掉的那些）。
