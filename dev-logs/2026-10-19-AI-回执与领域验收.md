# 2026-10-19 AI 架构第 ② 步：回执 + 领域验收（最小垂直链路）

## 起因

`PLAN.md` P22「AI 侧后续」，专项审查 §3.2（ActionReceipt）/ §3.3（Verifier），
以及 §6 给的落地顺序第 ② 条：**先覆盖库存移动/扣减和计划修改，形成最小垂直链路**。

**要解决的问题**：命令返回 `OK` 只说明"handler 没报错" ✗ ——
**不说明用户要的状态成立了** ✗（审查 §2.2 原话："格式正确、写盘成功、业务意图正确是不同层次"）。
所以会出现"执行了，但没做对"，而模型**没有任何证据**发现这件事、也就不会返工 ✗。

## 做了什么

新文件 **`src/services/ai_verify.py`**：

| 函数 | 作用 |
|---|---|
| `parse_command(cmd)` | 从命令行取 `(操作名, 参数)`（认 `--k v` 与 `--k=v` 两种写法） |
| `observe(cmd, data_dir)` | 执行**之前**记下关心的字段（回执的 `before`，也是"本来已满足"的判据） |
| `check(cmd, before, result, data_dir)` | 执行**之后**回读数据验收 → `(状态, 给模型的一句话)` |
| `summarize` / `mismatches` | 拼给模型看的 `[验收]` 段 / 挑出**没达到预期**的（给"汇报权归代码"用） |

**状态取值**（审查 §3.2 的语义）：

| 状态 | 含义 |
|---|---|
| `verified` | 目标状态成立 ✓ |
| `verified_noop` | 目标**本来就已经满足** —— **不是失败**（§2.1：验证后的无变化也算成功） |
| `mismatch` | 状态**不成立** → 模型该针对差异返工（而不是重复原命令） |
| `failed` | 命令自己就报错了（别把"执行失败"说成"验收不通过"） |
| `unverified` | 没有验收器 / 读不到数据 → **不许当成通过** ✗ |

**三条验收器**（判据全是"读 JSON 比字段"，**不请模型自查** ✓ —— §2.3 明确"模型不能自填验证通过"）：

- `consume`：余量必须**正好**少掉 `--amount`。特别注意"命令说 OK 但余量没变" → **`mismatch`** ✗
  （那是**不一致**，不是"无变化也算成功"）；
- `update_item --location`：位置必须等于 `canonical_location(目标)`（词表口径与生产同一处）；
  重复移到同一位置 → `verified_noop` ✓；
- `complete_plan`：那一条的 `done` 必须为真。

**接进 worker**（`ai_service.py`）：
- `_run_commands` 执行前 `observe`、执行后 `check`，把 `[验收]` 段**附在工具结果后面** ✓
  —— 模型这才有证据返工 ✓；
- 验收不一致的进"没生效"清单 ✓，最终文案改成
  "**N/M 条写命令没有生效或没达到预期**"（原来只说"没有生效"，装不下"生效了但没做对"）。

## 验证

新增 `tests/test_ai_verify.py`（**10 条**）：

- 命令行解析两种写法；
- 扣减：真跑一遍 → `verified`；桩数据"说 OK 却没扣" → `mismatch`；
- 移动：真跑 → `verified`，再移到同一处 → `verified_noop`，位置没变 → `mismatch`（带上实际值）；
- 计划完成：没标 → `mismatch`，标了 → `verified`；
- 没有验收器的操作 → `unverified`（**不许当通过**）；命令报错 → `failed`；
- **接进 worker**：`_run_commands` 的结果里必须出现 `[验收]` 与具体数字 `24 → 23` ✓；
  最终文案里必须出现"没有生效或没达到预期" ✓。

`git stash` 回旧代码：这几条无法直接对照（`ai_verify` 是新模块），
但"扣减/mismatch"两条是**桩数据驱动**的 —— 规则本身（"OK 不等于状态成立"）就是断言点 ✓。

**704 passed**（694 + 10）；`ruff` / `ui_tokens --strict --check-px` / `check_quality --strict`
全绿（**退出码全 0**）。

> 中途 `observe` 被 RADON 判成 **C(11)** ✗ → 拆成按操作的小助手 + `_OBSERVERS` 表 ✓。

## 诚实边界（没做完的部分）

- **只覆盖三条命令**（审查 §6 建议的起点）—— 其余操作一律 `unverified`，**不假装通过** ✗；
- 回执的**来源**是"命令文本 + 回读数据"，**不是**执行层返回的结构化对象 ✗ ——
  真正做到 §3.2 说的"回执来自执行层"，需要 `actions.py` 的 handler 返回结构化结果
  （现在 CLI 契约是纯文本）。当前形态已经能回答"用户要的状态成立了吗" ✓，
  但 `changed_fields` / `action_id` / 幂等键这些字段还没有；
- `rejected`（参数校验拒绝）与 `failed` 现在都归到 `failed` ✗ —— 精确区分同样要执行层给结构。

下一步（审查 §6 ③）：**任务账本 + 分类恢复** —— 逐目标 pending/verified/failed/blocked，
把"部分完成"按**目标覆盖率**报，而不是成功命令数。
