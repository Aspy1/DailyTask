## 二、脚本硬化（`scripts/actions.py`）

### 1) 非法输入：拒绝，且**一个字节都不写**

- 新增 `ActionError` + 校验层（`actions_core.py`），`run_in_process` 与 CLI 都在
  **handler 之前**调用 `_validate_args()`，失败只回 `ERROR ...`
- **数据驱动规格表** `SPECS`（22 条命令）：必填项、类型、范围、枚举、长度上限
- **未知参数直接拒绝**（旧实现 `--titel` 会被**静默忽略** → "看起来成功其实没写"）
- 具体规则：星期 1-7、节次 1-6、周次 1≤起≤止≤30、严格 YYYY-MM-DD（拒绝 2026-02-30）、
  金额 >0 且 ≤100 万、ID 形如 `t_001`、`--plans` 必须是合法 JSON 数组……
- 实测 12 类非法输入全部 `REFUSED` 且数据文件哈希不变

### 2) 写入：原子 + 写前备份 + 结构守卫

```
save(): 结构守卫(_validate_payload) → 备份旧文件 → 写 .tmp → 回读自检 → os.replace
```

- `load()` 遇到坏文件**明说**（`ActionError` + 提示用 restore），不再当成空数据继续写
  —— 那等于把用户数据清空
- 备份落 `data/backup/actions/<文件>.<时间戳>.json`，按设置里的
  `Backup.max_backups`（默认 10）轮转；该目录在 `.gitignore` 内（不会被 GitSync 推走）
- **手动恢复入口**：`list_backups` / `restore --name X --yes`
  （`--yes` 是硬门槛，提示词里也写明"AI 不得自行调用"；恢复前会把当前版本再备份一次）

### 3) 新增记账能力（此前 AI 完全不能记账）

`add_expense`（分类支持 id 或中文名，写入前按数据文件里的分类表校验）、`add_saving`、
`delete_expense`、`expense_summary`（月合计 + 分类 + 今日支出/存钱/月预算余额）。
命令总数 16 → 22。

### 4) 拆分（原文件 1391 行 > 规范上限 800）

| 文件 | 行数 | 职责 |
|---|---|---|
| `scripts/actions_core.py` | 757 | 数据读写（原子+备份）、参数校验、日期/课程名匹配 |
| `scripts/actions_cli.py` | 139 | argparse 子命令定义（纯声明） |
| `scripts/actions.py` | 711 | 命令实现 + 进程内执行器 + `main()` |

顺带修掉两处既有超限：`main()` 135 行（拆成 5 个 `_add_*_parsers`）、
`_validate_args` 109 行（改成规格表 + `_apply_rule`）。`AIService` 因余额逻辑外移也回到基线内。

## 决策原因

- **为什么坚持"校验与执行分离"**：校验写在 handler 里，任何一条新命令都可能漏校验；
  放在执行器统一入口（`run_in_process` / CLI 都过同一函数）才是"不可能绕过"。
- **为什么规格用数据表而不是 if/elif**：一是 22 条命令的 if/elif 会超函数长度与复杂度门禁，
  二是"参数规则"本质是数据；表 + 小函数既好读又能被测试交叉校验。
- **为什么拆文件而不是放宽 800 行上限**：上限的用途是"文件可读"；`actions.py` 1391 行里
  混了三层职责（读写/校验/命令），拆分是顺带把职责理顺，而不是为了过门禁而拆。
- **为什么备份目录放 `data/backup/`**：它已经在 .gitignore 里（不会被 GitSync 推走），
  而 `data/*.json` 本身有 git 历史兜底 —— 本地轮转备份 + 远端 git 历史互补。
