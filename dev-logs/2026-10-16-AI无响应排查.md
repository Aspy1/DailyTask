# 2026-10-16 · AI「迟迟未回复」排查与加固

## 用户报告

> 让 AI 帮忙导入本学期课程表，迟迟未回复，命令行未见 200 OK 之类的输出。

## 排查过程（证据链，而不是猜）

| 证据 | 结论 |
|---|---|
| `data/app.log` 最后一行 `[httpx2] INFO: POST .../go/openai/v1/chat/completions "HTTP/1.1 200 OK"`（23:11:31） | **请求成功了**，不是网络失败 |
| py-spy 抓运行中进程栈：主线程 `(idle)`、**没有 AI 工作线程** | 应用**没卡死**，请求早已结束、线程已回收 |
| 之后**再无任何日志**（成功路径的 "AI completed with N instructions" 没出现） | 解析出的命令数 = 0 |
| 数据**一条没变**（`data/backup/actions/` 无新备份、`sem_001` 课表仍 0 门） | 命令一条都没执行 |
| 实测复现：只说"帮我导入课程表" → 6.3s、0 命令（模型反问要素） | 少信息时会**只回文本** |
| 实测复现：带 24 门课表 → 40–58s、24 命令（推理 token 占一半） | 长回复会**很慢且很长** |

**结论**：模型回复**没被解析出命令**。最可能是**回复撞输出上限被截断** ——
`InstructionParser.parse` 的正则要求有收尾 ```，截断后**整段丢弃**，
既不执行也不提示。用户看到的就是"AI 没反应"。

顺带确认：**没有 200 OK 输出是正常的**（我之前把 httpx 降到 WARNING 了），
但应用对 AI 请求**完全没有生命周期日志** —— 用户盯着日志等，什么也看不到。

## 修了什么

| 改动 | 位置 | 为什么 |
|---|---|---|
| `parse` 容忍**未收尾**的 ```sh 块，完整行照执行 | `ai_service.InstructionParser` | 截断后至少把这批做完；每行都过 `actions.py` 严格校验，非法行会被拒绝 |
| 检测截断（围栏数为奇数）→ 让模型**分批续跑** | `AIWorker.run` | 自愈：告诉模型"被截断了，每轮 ≤8 条继续" |
| 提示词新增"一次很多条要分批（每轮 ≤8）" | `SYSTEM_PROMPT_BASE` | 从源头减少截断 |
| **生命周期日志**：`AI turn N: 耗时 | 字符数 | 疑似截断 | 命令数` | `AIWorker.run` | 用户就是盯着日志等的 |
| 模型客户端 **120s 超时** | `DeepSeekProvider` | SDK 默认 10 分钟；卡住时用户干等且无提示 |
| 空回复给明确提示 | `AIService._on_response` | 界面一片空白 = "AI 没反应" |

## 我犯的一个错（记录）

写 ad-hoc 探针时调了 `scripts.actions.run_in_process` 却**没有先把
`actions_core.DATA` 指到临时目录**，于是把一条测试任务（"背包问题"）写进了
真实 `data/semesters/sem_001/tasks.json`。

发现后用它自己的备份机制回滚（`restore --name tasks.json --yes`）并清掉备份痕迹。
教训：`tests/helpers.run()` 的"误写真实数据"守卫只保护 **pytest 测试**，
ad-hoc 脚本没有这层保护 —— 探针脚本**第一件事**就该钉数据目录。
