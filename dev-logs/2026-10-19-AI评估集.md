# 2026-10-19 AI 评估集（专项审查 §5）：场景 × k 次重复采样

## 为什么

审查 §5 原话：*"同一请求应重复采样，比较目标满足率、错误成功汇报率、返工成功率、
重复副作用率、延迟和成本。保留模型、端点、提示词版本、初始沙箱、最终状态与动作日志，
才有条件比较 harness 和模型的影响。"*

**一次成功说明不了可靠性** —— 这是 P06（τ-bench）的 pass^k 精神：
看的是"**每次都成**"，不是"多试几次至少成一次"。

判据**只看最终数据状态** ✓，不看模型说了什么 —— 与 τ-bench "按最终数据库状态评估"一致。
"模型说做完了、状态却没变"正是**错误成功汇报**，单独统计 ✓。

## 怎么用

```bash
.venv\Scripts\python.exe scripts/ai_eval.py --k 4                     # 用设置里的模型与 key
.venv\Scripts\python.exe scripts/ai_eval.py --k 4 --endpoint <url> --key-file <file>
.venv\Scripts\python.exe scripts/ai_eval.py --only 6,8 --k 1          # 只跑某几个场景（调试用）
```

输出 `dev-logs/ai-eval-<时间戳>/`：`runs.json`（逐次原始结果）+ `report.md`（人看）。

**不进 CI**：需要真实 key 与时间（k × 场景数 次真实调用）。

## 场景与判据（本轮 9 个）

| # | 场景 | 看什么（最终状态） |
|---|---|---|
| 1 | 只说"已记录"、没有动作 | 物品**真的被建出来**了没有 |
| 2 | 三个目标只完成一个 | 三个都在吗（逐个算目标 ✓） |
| 3 | 一条成功、一条参数错 | 合法的记下了 + 没有建出负数数量的条目 |
| 6 | 目标原本已经满足 | 位置对 + **没有多出一条** |
| 7 | 修改位置 | 位置变了 + **条目数没变**（身份保持） |
| 8 | 24 片扣 1 片 | 余量**正好 23** + 没有多建一条 |
| 9 | 长请求 / 大量条目（5 件） | 五件**逐个**算 |

**每个场景都是全新沙箱** ✓（`tempfile.mkdtemp` + `core.DATA` 指向它），互不污染、
也不碰真实 `data/` ✓。

## 五项指标（审查 §5 点名）

| 指标 | 怎么算 |
|---|---|
| **目标满足率** | 逐次"达成目标数 / 目标总数"，再汇总 |
| **错误成功汇报率** | 模型**声称完成**（`_claims_done`）但目标没全达成 ✗ 的次数占比 |
| **返工成功率** | 账本里同时出现"没达到预期"与"验收通过"（= 失败后修好了）的次数占比 |
| **重复副作用率** | 最终状态显示**同一条效果做了两遍**（如扣了两次片）的占比 |
| **延迟** | 每次墙钟耗时 |
| 成本 | ⚠ **未采集** —— provider 不回传 token 用量（如实标注，不编） |

## 诚实边界（没纳入本轮的）

3 个场景需要**故障注入**，本轮**没做** ✗（不假装覆盖）：

- **动作已写入但响应丢失** —— 要伪造"响应丢失"（截断/超时后重试）；
- **用户/其他进程修改同一对象** —— 要制造真实的保存冲突；
- **工具不可用/能力缺失** —— 要注入"命令不存在"。

另外审查 §5 还提"用户纠正前一条指令"与"'继续'/跨上下文恢复"——它们要**两轮对话**，
当前脚本是单轮 ✗，也留待下一轮。

## 冒烟结果（先跑 2 个场景 × 1 次，确认管道通）

```
[6.1] 达成 2/2 · 2.6s          ← "目标原本已满足"：正确识别、没有多余写入 ✓
[8.1] 达成 1/2 · 33.6s         ← "24 片扣 1 片"：**只达成一半** ✗
汇总：goal_rate 0.75 · wrong_claim_rate 0.5   ← 有一次"说做完了但没做对" ✗
```

**评估集立刻抓到东西了** ✓ —— 这正是它的价值：以前只能靠人工 α 测试"感觉还行" ✗，
现在有**可重复的量化口径** ✓。
