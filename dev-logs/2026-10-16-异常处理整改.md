## 两类问题与处置

### 1. `S110` 静默吞异常（真正的"静默失败"源头）→ 全部改为带 `exc_info` 的日志

用 AST 精确匹配「handler 体恰好只有一条 `pass`」的 try/except，**替换 40 处**
（ruff 只报 24 处，因它默认不检查"已指定类型"的 except），并为缺少 `logger` 的模块自动补齐
`import logging` + `logger = logging.getLogger(__name__)`。

替换形式：

```python
logger.debug("HabitModel.is_active_today 中忽略异常", exc_info=True)
```

> 选择 `debug` 而非 `warning`：这些多是"可忽略"路径（解析回退、清理、best-effort），
> 平时不输出，出问题时把日志级别调到 DEBUG 即可看到完整栈。

### 2. `BLE001` 盲捕获 → 分两类处置

**收窄（6 处）** —— 异常类型明确：

| 位置 | 收窄为 |
|---|---|
| `ai_service._fetch_deepseek_balance` | `(OSError, ValueError, KeyError, TypeError)` |
| `ai_service._fetch_weather_for_prompt` | 同上（`requests.RequestException` 继承自 `IOError`→`OSError`，已覆盖网络） |
| `api_service.get_weather_sync` / `get_balance_sync` | 同上 |
| `scene_archive` 导出 / 建场景 | `(OSError, ValueError, TypeError, KeyError, zipfile.BadZipFile)` |

**标注边界（15 处）** —— 确属边界，保留 `except Exception` 但写明理由并 `# noqa: BLE001`：

- 线程入口：`AIWorker.run`、`_ApiWorker.run`、`_GitWorker.run`、`WeatherWorker.run`
- 事件循环槽 / 清理路径：`src/ui/**`
- 第三方代码加载：`plugin_manager`（插件 `register`/`factory` 可能抛任意异常）
- 外部服务：`reminder_service._send_email`（SMTP）、`send_digest`
- CLI 边界：`scripts/actions.py`（任何 handler 异常都必须转为 `ERROR ...` 输出而非崩溃）

**配置**：`pyproject.toml` 增 `"src/ui/**" = ["BLE001"]`，附理由注释
（Qt 槽函数与主题刷新/清理路径**不允许异常逃逸进事件循环**）。

## 教训

- ruff 的 `S110` 只覆盖"裸 pass"，**具名 `except X: pass` 同样是静默吞异常**；用 AST 才能查全（24 → 40）。
- "吞异常"和"边界捕获"是两回事：前者掩盖 bug，后者是必要的架构边界。
  规范必须给出**二选一的可执行判据**，否则要么全禁（做不到）、要么全放（没意义）。
- 修完立刻在 `pyproject.toml` 里把**豁免写成配置+理由**，而不是散落在代码里靠自觉。
