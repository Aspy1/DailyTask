## 2. 定位证据（先复现，再动手）

### 2.1 保存路径：86% 花在 `json.dump`

`scripts/perf_profile.py`（10k 条 × 10 次保存，cProfile 累计耗时）：

```
10 次 save()                    8.212 s
└─ atomic_write                 7.057 s
   └─ json.dump(indent=2)       6.987 s   ← 85%
      ├─ _iterencode            4.703 s   （纯 Python 编码器）
      ├─ _iterencode_dict       3.886 s
      └─ TextIOWrapper.write    1.009 s   （5,400,170 次调用！）
   └─ _read_disk_state          0.773 s   ← 冲突检测读盘解析
```

**根因**：`json.dump(..., indent=2)` 因为有缩进与非 ASCII，只能走**纯 Python**
编码分支，且每几个字符调用一次 `write()` —— 10k 条就是 540 万次写调用。

### 2.2 面板构造：67% 花在首屏之外

`scripts/perf_panel_costs.py`（各面板单独构造，中位数）：

| 面板 | 耗时 |
|---|---|
| `ScheduleView`（首屏） | 27.17 ms |
| `SettingsPanel` | 28.01 ms |
| `TaskPanel` | 7.20 ms |
| `ExpensePanel` | 6.91 ms |
| `StudyPanel` | 5.16 ms |
| `InventoryPanel` | 3.99 ms |
| `RoutinePanel` / `ExamPanel` / `HabitPanel` | 1.1 / 1.1 / 0.9 ms |
| **合计** | **81.56 ms** |
| **首屏之外（可延迟）** | **54.39 ms（67%）** |

### 2.3 一个必须先修的测量缺陷

第一版对照量出"两种模式都是 ~104 ms，毫无差别"。原因不是产品没差异，而是
**测量边界包含了 `write_fixture` 的磁盘写入与 `DataManager` 初始化** ——
手册 §1.3 要求"定义操作起止点"，数据准备属于场景前置，不能计入。
修正边界后差异立刻显现（见 §3.1）。**同一轮还发现第二个缺陷**：
`main_workspace` 用 `from panel_factory import LAZY_PANELS` **按值复制**，
运行期改开关无效 → 回退路径从未被真正执行过。改为读模块属性后才有真实对照。

## 3. 方案对照结果

### 3.1 方案 A：Qt 内消除阻塞

**A-1 首屏延迟构建**（`scripts/perf_panel_bench.py --full`，**三档全测**）：

| 场景 | 档位 | 基线中位 | 候选中位 | 改善 | P95 改善 |
|---|---|---|---|---|---|
| 工作区构造 | 1k | 129.00 ms | **85.85 ms** | **+33.4%** | +69.7% |
| 工作区构造 | 10k | 189.00 ms | **148.54 ms** | **+21.4%** | +75.3% |
| 工作区构造 | 50k | 302.91 ms | **217.59 ms** | **+28.2%** | +41.7% |
| 首次切作业 | 1k | 140.79 ms | **114.03 ms** | **+19.0%** | +70.6% |
| 首次切作业 | 10k | 217.09 ms | **177.44 ms** | **+18.3%** | +86.9% |
| 首次切作业 | 50k | 335.97 ms | **272.97 ms** | **+18.8%** | +89.8% |
| 重复切作业 | 1k | 9.74 ms | 9.99 ms | −2.5% | −12.2% |
| 重复切作业 | 10k | 16.24 ms | 15.27 ms | +6.0% | −3.4% |
| 重复切作业 | 50k | 25.83 ms | 23.33 ms | +9.7% | +8.9% |
| 全页切换 10 项 | 1k | 181.29 ms | 202.80 ms | **−11.9%** | **+78.6%** |
| 全页切换 10 项 | 10k | 266.18 ms | 282.86 ms | **−6.3%** | **+86.7%** |
| 全页切换 10 项 | 50k | 391.80 ms | 433.41 ms | **−10.6%** | **+86.1%** |

原始样本：`dev-logs/perf-data/panel-lazy-construction.json`（含每档每场景的逐次耗时）。

**结论（如实）**：

- **三档同向**：构造改善 +21~33%、首次切页 +18~19% —— 延迟构建的收益
  **不随数据量变化**（面板构造成本与条数无关，符合预期）；
- **代价一致**：全页切换中位 **−6~−12%**，三档都是这个量级 —— 延迟构造把成本从启动
  搬到"首次进入"，总量不变；
- **尾部大幅收敛**：全页切换 P95 三档分别 **+79% / +87% / +86%**
  （1k：1031→220 ms，10k：2292→304 ms，50k：3273→455 ms）。基线尾部尖峰来自
  一次性构造 8 个面板 + GC 抖动，现在被摊平了 —— 手册要求"逐笔检查尾部"，
  这一项是实打实的收益。

**取舍判断**：采用。启动是**唯一不能等**的场景；"全页切换"是用户逐页浏览的
累计值，一次只多 ~20 ms（50k 下 392→433 ms 是**十次切换的总和**），单页感知不到。

**A-2 保存路径编码**（`scripts/perf_baseline.py`，n=50）：

| 数据档 | 基线中位 | 候选中位 | 改善 | 基线 P95 | 候选 P95 |
|---|---|---|---|---|---|
| 1,000 条 | 28.12 ms | **20.02 ms** | **+28.8%** | 30.72 | 21.39 |
| 10,000 条 | 244.64 ms | **168.25 ms** | **+31.2%** | 291.63 | 198.67 |

**做法**：`json.dump(f)` → `json.dumps()` + 一次 `write()`。**输出字节完全相同**
（`tests/test_save_encoding.py` 逐字节钉住，**含 CRLF**：Windows 文本模式的换行
必须原样保留，否则整份文件会在 git diff 里重写）。

**顺带修掉的真缺陷**：`atomic_write` 失败时会把 `*.tmp` 留在数据目录（改造前复现）。

**A-3 刷新合并**：**缩小范围后采用**。原计划对所有事件合并，但
`tests/test_data_flow.py` 抓到：外部写入后推迟到下一轮事件循环 = 用户可见回归。
最终只对 `ai_action` / `ai_undo`（一次操作连发多个事件的批量场景）合并，
单域事件**保持同步**。验证时还发现一个**真实 bug**：`_refresh_by_panel` 拿导航键
（`tasks`）去比对域名集合（`task`），单复数不符 → 事件**静默不刷**，只有
`inventory` 恰好同名才正常。已加 `KEY_TO_DOMAIN` 映射 + 逐键守卫测试。

### 3.3 方案 C：作业 SQLite 原型

`scripts/perf_sqlite_bench.py`（同数据、同操作边界，n=50）：

| 操作 | JSON 中位 | SQLite 中位 | 中位改善 | P95 改善 |
|---|---|---|---|---|
| 按学期列表（10k） | 41.20 ms | 103.50 ms | −151.2% | -160.8% |
| 未完成筛选（10k） | 42.43 ms | 68.74 ms | −62.0% | -70.9% |
| 分页 100 条（10k） | 43.07 ms | 0.50 ms | +98.8% | +98.8% |
| 单条完成（10k） | 77.75 ms | 0.02 ms | +100.0%（取整） | +100.0% |
| 批量导入（10k） | 76.93 ms | 106.99 ms | −39.1% | -49.0% |

1k 档单条完成 8.52 → 0.03 ms，分页 3.94 → 0.51 ms。两侧在每次预热与采样前恢复为待完成，准备动作在计时外，每次都检查是否真实更新。数字来自 `perf-data/sqlite-comparison.json`。

**结论：不建议整体切换；值得为"单条写入"试点。**
"全量列表 / 筛选"SQLite 反而慢，因为每行都要建 Python dict；而本项目列表操作
走的是**内存态模型**（一次载入、多次读），JSON 侧那 40 ms 是"整份解析"成本 ——
SQLite 替不掉它。原型使用 SQLite WAL 和 `synchronous=NORMAL`，JSON 侧测读改写，未经过生产的回执、验证与备份链。这组微基准适合筛选试点，实装前仍需测端到端延迟与相同恢复目标下的持久性。

原型已具备切换所需的正确性保障（`tests/test_task_store_sqlite.py`，12 条）：
学期隔离、分页不重不漏（稳定 tie-breaker）、完成幂等、导入幂等（UPSERT）、
schema 版本拒绝、在线备份可恢复、事务回滚、查询计划走索引。

**若后续实装**，按手册 §4.3 的演练顺序：预检 → 备份 → 暂停该域写入 → 导入 →
核对 → 切换消费者 → 恢复写入，并保留 JSON 作为导入来源。

## 8. 进程树内存（手册 §2.2 口径）

手册要求用**系统指标**、以"进程树私有提交量"为口径（不重复计算共享页），
而不是拿 `tracemalloc` 当总内存。新增 `scripts/perf_memory.py`
（`GetProcessMemoryInfo` 的 `PrivateUsage` + Toolhelp 子进程枚举）。

⚠ 第一版在**同一进程里连跑两种模式**，量出"延迟模式反而多 20~33 MiB"——
那是污染（Qt 对象回收不及时 + allocator 复用，后跑的那次永远更高）。
改成**每个模式一个全新子进程**后：

| 场景 | 全构造 | 首屏延迟 | 差异 |
|---|---|---|---|
| **稳态**（逐页浏览后） | 126.4 MiB | 126.1 MiB | **−0.3 MiB**（相同） |
| **起点**（不点任何页） | 114.5 MiB | **84.5 MiB** | **−30.0 MiB**（−26%） |

原始样本：`dev-logs/perf-data/memory-panels.json`（每档 5 轮的逐轮私有提交量，
可复核离散程度；不是只给一个汇总数）。

结论：延迟构建**不增加**稳态内存（两种模式最终都持有同样的 8 个面板），
而首屏起点少占约 30 MiB。手册 §3.4 要求的"为稳定内存约定可接受的额外开销"
因此是 **0 额外开销**，验收通过。

## 9. 方案 C 的决策（按预算判定，不留给人工裁决）

手册 §3.4 要求"试验前先为主要指标定预算"。把这条规则落成可执行判据
（`scripts/perf_sqlite_decision.py`，`tests/test_perf_decision.py` 守 6 条），
预算统一为"最低可接受改善百分比"（改善为正、变慢为负）：

| 指标（10k 档 P95） | 实测 | 预算 | 判定 |
|---|---|---|---|
| 单条完成 | **+100.0%** | ≥ +20%（手册示例） | ✅ |
| 分页 100 条 | **+98.8%** | ≥ 0% | ✅ |
| 全量列表 | **−160.8%** | ≥ −20% | ❌ |
| 批量导入 | **−49.0%** | ≥ −20% | ❌ |

**决策：整体切换预算通过 2/4。单条写入指标达到原型预算，可进入端到端试点。** 生产切换仍需为作业使用单一权威存储，并同步验证其读取方及回退。

复核方式（三条命令，都可重跑）：

