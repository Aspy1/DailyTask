## 1. 范围

本次只做一件事：**`TaskDetailDialog._on_save()` 保存失败时，把内存里的任务改回保存前的样子**。

原来的顺序是：

```
notes/attachments → dm.tasks.update()（就地改内存 + 盖 updated_at）
                  → dm.tasks.save()（写盘，冲突时返回 False）
```

`save()` 返回 `False` 时只弹了"保存失败"，**内存已经被改过了**。于是内存比磁盘多一份
改动 → 应用退出 / 重启走 `DataManager.flush_on_exit()` 时会发现"磁盘和内存不一致"，
判定成外部改动，把这份**根本没保存成功**的改动刷成一份冲突副本文件。用户看到的是
"保存失败"，磁盘上却多出一个副本，下次还得人工判断该用哪份。

修复后的顺序：

```
先快照 notes / attachments / updated_at（含"键存不存在"）
  → update() → save()
      ├─ True ：照旧（删文件、清 _added、发信号、accept）
      └─ False：按快照原样还原内存 + 弹原来的警告 + 一个文件都不删
```

刻意保持不变的：

- **成功路径一行没改**（仍然先写索引、成功后才 `_commit_removals()` 删文件）；
- **弹的还是原来那条警告**（`dialog.task.msg_save_failed`），没有新文案；
- **对话框里用户改的内容留着**（`_entries` / `_removed` / 备注控件都不动）——失败不是
  "丢弃编辑"，用户重试一次还能成功；
- **失败时一个文件都不删**（`_commit_removals()` 在 `return` 之后，走不到）。

"原样还原"包含**键的存在性**：老数据（`tasks.json` 里没有 `attachments` 键）失败回滚后
仍然是"没有这个键"，不能留一个 `[]` 空壳 —— 否则等于在内存里把老 schema 悄悄升级了，
下一次保存就把新键写进磁盘。
